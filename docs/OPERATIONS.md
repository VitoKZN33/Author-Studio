# Эксплуатация

## Состояние

```bash
./scripts/status.sh                 # контейнеры + проверки БД, Redis, фонового обработчика
docker compose logs --tail=100 api worker
```

HTTP: `/api/health/live` (процесс жив), `/api/health/ready` (БД и Redis),
`/api/health/status` (включая фоновый обработчик). Коды: 200 — норма, 503 — сбой.

## Логи

JSON (pino) в stdout контейнеров; Docker ротирует их (10 МБ × 5 файлов на сервис).
Секреты из конфигурации и распознаваемые по формату (токены ботов, пароли в URL,
Bearer, `sk-`-ключи) заменяются на `[СКРЫТО]`. Строка запроса URL в логи не
пишется. Каждому запросу присваивается `requestId`; он же возвращается в ответах
об ошибках — по нему ищется запись в логе.

## Публикации

Статусы отправки: «Запланировано» → «Отправляется» → «Опубликовано» / «Ошибка» /
«Результат неизвестен». Последний означает, что связь с Telegram прервалась после
отправки запроса: проверьте канал и отметьте результат в приложении (повтор вслепую
мог бы создать дубль). Каждая попытка записывается в таблицу `publication_attempts`.
Медиафайлы хранятся в томе Docker `media`.

## Резервные копии

`./scripts/backup.sh` — `pg_dump -Fc` и архив медиафайлов в `./backups`, проверка через
`pg_restore --list`, хранение последних 14 копий (`BACKUP_KEEP`). Расписание (cron),
восстановление и вынос копий за пределы сервера — этап 8 (`docs/BACKUP_RESTORE.md`).

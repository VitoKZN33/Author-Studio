# Тестирование

## Команды

| Команда                 | Что делает                                                                                                     |
| ----------------------- | -------------------------------------------------------------------------------------------------------------- |
| `pnpm check`            | форматирование (Prettier), линтер (ESLint), сборка всех пакетов, проверка типов, unit-тесты, проверка миграций |
| `pnpm test`             | unit-тесты всех пакетов (Vitest)                                                                               |
| `pnpm test:integration` | интеграционные тесты сервера с настоящими PostgreSQL и Redis                                                   |
| `pnpm check:migrations` | поиск разрушающих операций в SQL-миграциях                                                                     |
| `pnpm audit --prod`     | известные уязвимости production-зависимостей                                                                   |

Интеграционным тестам нужны переменные:

```bash
export TEST_DATABASE_URL=postgresql://app:apppw@127.0.0.1:5432/author_studio_test
export TEST_REDIS_URL=redis://127.0.0.1:6379
pnpm test:integration
```

Перед прогоном тесты **полностью очищают** схему этой БД и Redis (FLUSHDB) —
указывайте только отдельную тестовую базу. Без переменных тесты падают, а не
пропускаются. В CI (GitHub Actions) поднимаются PostgreSQL 17 и Redis 8.

## Что покрыто

Unit (118 тестов):

- проверка конфигурации окружения: значения по умолчанию, русские сообщения об
  ошибках, длина ключа шифрования, часовой пояс, https в production, токен бота
  не попадает в текст ошибки;
- фильтр секретов в логах: известные значения, токены ботов, пароли в URL, Bearer,
  `sk-`-ключи, пути redact;
- очистка metadata журнала событий от секретных полей;
- агрегирование состояния здоровья;
- полнота русского словаря интерфейса;
- проверка initData: корректная подпись, поле signature, подмена user, чужой токен,
  просрочка, «будущая» дата, повторяющиеся ключи, отсутствие пользователя, длина;
- классификация ошибок Bot API (429 с retry_after, 5xx, 4xx, 401, сеть);
- права бота в канале и статусы; разбор адреса канала (@username, t.me, ID,
  приватные ссылки);
- группировка каналов на экране;
- содержимое публикации: все лимиты Telegram, UTF-16, кнопки, ссылки, повторы файлов;
- часовые пояса: перевод времени установки в UTC, переходы на летнее/зимнее время;
- редактор: преобразование документа в текст + entities и обратно без потерь;
- определение типа медиафайла по сигнатуре; классификация «запрос мог быть обработан»;
- сетка календаря, группы публикаций;
- аналитика: ряды по дням с пропусками, изменение за период, значение «на момент»,
  изменение за 24 ч с базой, ERR, лучшее время и пороги выборки, шкала цвета;
- шифрование секретов: подмена шифртекста/тега/AAD, короткий тег, чужой мастер-ключ, маска;
- клиент AI: коды ошибок, повторы, тайм-аут, нет соединения, не-JSON, пустой ответ,
  отказ от response_format, ключ не попадает в текст ошибки; извлечение JSON из ответа;
- подсказки AI: данные в разделителях, проверка чисел, которых нет в данных;
- разметка AI ↔ entities (жирный, ссылки, UTF-16, только http(s)).

Интеграционные (100 тестов, Bot API и AI-провайдер имитируются локальными HTTP-серверами):

- миграции: таблицы, строка настроек, идемпотентный повторный запуск, ограничения
  целостности (singleton, уникальный `telegram_id`);
- BullMQ: отложенное задание, поставленное без воркера, выполняется после запуска
  воркера; задание аварийно упавшего воркера подхватывает новый; повторный `jobId`
  не создаёт дубликат;
- API: live/ready/status, 503 без воркера и 200 после запуска, снятие heartbeat
  при корректной остановке, 404 в едином формате без стектрейса, 413 для тела > 1 МБ,
  защитные заголовки;
- API при недоступной БД: live = 200, ready = 503, адрес БД не раскрывается;
- журнал событий: запись и отбрасывание секретных полей;
- вход: токен владельцу, хэш в БД, подделка, просрочка, чужой пользователь (403 +
  журнал), валидация тела, 401 для всех вариантов отсутствующей/плохой сессии,
  выход, истечение, лимит сессий, лимит частоты (429);
- webhook: секрет, дедупликация по update_id;
- каналы: все сценарии подключения, повторная проверка, отключение, IDOR;
- полный путь webhook → очередь → worker: обнаружение канала и уведомление, игнор
  чужого добавления, удаление бота, повтор уведомления после 429, `/start`;
- публикации: черновики и конфликт версий, медиа (сигнатуры, лимиты, доступ),
  немедленная и отложенная отправка, перенос, отмена, альбом и file_id, 429,
  обрыв связи (`ambiguous`) и решения владельца, отказ соединения, постоянная ошибка
  и повтор, гонка исполнителей, перезапуск worker, реконсилятор, канал без прав,
  настройки уведомлений, календарь, IDOR;
- аналитика: сбор подписчиков (в том числе при ошибке Telegram), сводка с пропусками,
  обновления channel_post / реакции / chat_member без персональных данных, привязка
  публикаций, ручной ввод и ERR, лучшее время, CSV и отправка в чат;
- AI: ключ (шифрование, маска, удаление, отсутствие в API и журнале), проверка
  подключения и ошибки провайдера, текст поста, ответ не по схеме, лимиты суток и
  месяца, учёт расхода, контент-план и черновики, разбор аналитики, 404 для чужого
  канала, 401 без сессии.

Замечание: зависшее задание BullMQ возвращается в очередь через `stalledInterval`
(в production — 30 с). Тест использует 1 с.

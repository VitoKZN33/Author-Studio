# Архитектурные решения (ADR)

Статус «предложено» — до подтверждения владельцем проекта.

**ADR-001. Модульный монолит NestJS, процессы `api` и `worker`.** Предложено.
Один код, общие модули, раздельные точки входа. Микросервисы не нужны для одной
установки на одного владельца.

**ADR-002. PostgreSQL — источник истины заданий, BullMQ — доставка.** Предложено.
Состояние публикаций и рекламных действий живёт в БД; реконсилятор восстанавливает
задания после потери Redis или простоя. `jobId` = id сущности против дублей.

**ADR-003. Next.js в режиме static export, без Node-контейнера frontend.** Предложено.
Mini App работает внутри Telegram, SSR и SEO не дают пользы; публичный отчёт —
клиентская страница с запросом к API. Минус один сервис, меньше поверхность атаки.
Ограничение: нельзя использовать серверные компоненты/route handlers Next.js.

**ADR-004. Caddy вместо Nginx + certbot.** Принято владельцем 2026-10-25.
Автоматическое получение и продление сертификатов встроено. ТЗ допускает Nginx
«если схема этого требует».

**ADR-005. ORM и миграции отдельным шагом.** Заменено ADR-016 в части ORM.
Миграции только расширяющие (expand → contract в следующем релизе), резервная
копия перед каждой миграцией в `update.sh`.

**ADR-006. grammY как клиент Bot API, webhook с `secret_token`.** Предложено.
Типизированный клиент, без собственной реализации транспорта. Для локальной
разработки — long polling.

**ADR-007. Форматирование через `entities`, а не HTML/Markdown parse_mode.** Предложено.
Редактор (TipTap/ProseMirror с урезанной схемой) → собственный документ → entities
с UTF-16 смещениями. Исключает ошибки экранирования.

**ADR-008. Авторизация: initData → непрозрачный токен в заголовке, без cookies.** Предложено.

**ADR-009. Владелец задаётся `OWNER_TELEGRAM_ID` при установке.** Предложено.
Альтернатива — одноразовый код привязки через `/start <код>`; можно добавить позже.

**ADR-010. Автор неоднозначного результата отправки — человек.** Предложено.
При сетевой ошибке после отправки запроса статус `AMBIGUOUS`, без автоповтора —
дубль рекламы в канале хуже, чем ручная проверка.

**ADR-011. Тесты — Vitest (unit/integration с реальными Postgres/Redis через
Testcontainers или compose), Playwright для UI.** Предложено.
В ТЗ (раздел 20) упомянут pytest — для TypeScript-стека его заменяет Vitest.

**ADR-012. Версии зависимостей.** Предложено. Сверено с реестром npm и
nodejs.org 2026-10-25; точные версии фиксируются lock-файлом на этапе 2.

**ADR-013. Просмотры и пересылки в MVP — ручной ввод.** Принято 2026-10-25.
Источник `manual` с пометкой в UI; MTProto-коннектор не реализуется. Модель данных
допускает другие источники в будущем.

**ADR-014. Название по умолчанию — «Author Studio».** Принято 2026-10-25.
Конфигурируется в настройках установки.

**ADR-015. Рекламный модуль ориентирован только на РФ.** Принято 2026-10-25.
Следствия: поля маркировки (ERID, ИНН/наименование рекламодателя, договор, акт)
входят в основную модель заказа; предупреждение при публикации рекламы без ERID;
шаблон пометки «Реклама. … erid: …»; ежемесячное напоминание о передаче статистики
в ОРД; ручной ввод показов для отчёта в ОРД; валюта по умолчанию — RUB.
Регуляторный риск R-2 сохраняется и отслеживается перед этапом 6.

**ADR-016. Drizzle ORM вместо Prisma.** Принято владельцем 2026-10-25 (этап 2).
Prisma 7 для миграций скачивает бинарный schema-engine с binaries.prisma.sh — это
внешняя зависимость сборки на сервере каждого покупателя (и домен закрыт в рабочей
среде разработки). Drizzle — чистый TypeScript: SQL-миграции генерируются
`drizzle-kit generate`, хранятся в репозитории (`apps/server/drizzle/`), проверяются
на разрушающие операции (`scripts/check-migrations.mjs`) и применяются встроенным
мигратором `drizzle-orm` без бинарников.

**ADR-017. Backend — ES-модули.** Принято (этап 2). NestJS 12 распространяется как
ESM; сервер собирается в ESM (`"type": "module"`, `module: NodeNext`).
Пакет `@author-studio/shared` остаётся CommonJS для совместимости с Next.js и Node.

**ADR-018. Миграции применяются сервисом `migrate` при каждом запуске compose.**
Принято (этап 2). Это сохраняет рабочий цикл `git pull && docker compose up -d --build`.
Защита: разрешены только расширяющие миграции, разрушающие требуют пометки
`destructive-approved` после ревью; `scripts/update.sh` делает резервную копию до
обновления.

**ADR-019. Зависимостям запрещены сборочные скрипты по умолчанию.** Принято (этап 2).
Разрешения перечислены в `pnpm-workspace.yaml` (`allowBuilds`); телеметрия
`@scarf/scarf` запрещена; телеметрия Next.js отключена при сборке.

**ADR-020. Официальный скрипт telegram-web-app.js вместо SDK-обёртки.** Принято (этап 3).
Для входа и базовой интеграции (initData, тема, подтверждения, тактильный отклик)
достаточно официального скрипта; меньше зависимостей и нет расхождений с клиентом
Telegram. `@tma.js/sdk-react` подключим, если понадобятся его возможности.
Риск — доступность telegram.org из WebView (RISKS.md, R-15).

**ADR-021. Webhook, кнопка меню и команды регистрируются worker'ом при старте только
в production** (или при `TELEGRAM_AUTO_SETUP=true`). Иначе локальный запуск с тем же
токеном перехватил бы webhook рабочей установки.

**ADR-022. Канал учитывается, только если бота добавил сам владелец** (поле `from`
в `my_chat_member`), а при подключении по адресу сервер проверяет, что владелец —
администратор канала. Это закрывает подключение чужих каналов через одну установку.

**ADR-023. Уведомления владельцу — через очередь `notifications`** с лимитом 1 сообщение
в секунду, учётом `retry_after` (очередь ставится на паузу без траты попытки) и
схлопыванием одинаковых событий в окне 5 минут. Настройки категорий уведомлений —
вместе с публикациями (этап 4), когда категорий станет больше одной.

**ADR-024. Прокси для Bot API и режим polling.** Принято (этап 3, по результатам
проверки на сервере в РФ: api.telegram.org недоступен из дата-центра).
`TELEGRAM_PROXY_URL` (SOCKS5 / HTTP CONNECT) применяется ко всем запросам бота.
`TELEGRAM_UPDATES_MODE=polling` — worker забирает обновления `getUpdates` через тот же
прокси и кладёт их в ту же очередь, что и webhook; смещение хранится в Redis.
Webhook остаётся режимом по умолчанию для серверов с прямым доступом к Telegram.

## 2. Публикации

## 3. Права бота в канале и операции

| Операция                                                                                                                                  | Требуемое право                                                              | Статус |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------ |
| Публикация                                                                                                                                | `can_post_messages`                                                          | 📘     |
| Редактирование чужих постов                                                                                                               | `can_edit_messages`                                                          | 📘     |
| Закрепление в канале                                                                                                                      | `can_edit_messages` (в каналах закреп завязан на право редактирования)       | 📘 🧪  |
| Удаление: бот с `can_post_messages` удаляет свои сообщения; с `can_delete_messages` — любые                                               | ✅ (текст deleteMessage)                                                     |
| **Правило 48 часов** у `deleteMessage` стоит первым пунктом списка; из документации не ясно, снимают ли его права администратора в канале | ✅ текст / 🧪 поведение                                                      |
| Изменение прав/удаление бота                                                                                                              | приходит `my_chat_member` → статус канала обновляется, владелец уведомляется | 📘     |

⚠️ Правило 48 часов критично для рекламы «1/72», «1/7 дней». До подтверждения на
реальном канале UI будет предупреждать, что автоудаление позже 48 ч может не
сработать, и при ошибке переводить размещение в «требует ручного удаления».

### Варианты получения просмотров и пересылок

1. **Ручной ввод** владельцем (с пометкой «введено вручную»). Работает всегда.
2. **Опциональный коннектор Client API (MTProto) с аккаунтом самого владельца**:
   официальный API Telegram, `api_id/api_hash` владелец получает сам на
   my.telegram.org, сессия хранится зашифрованной только на его сервере. Даёт
   просмотры, пересылки и статистику канала. Риски: ограничения/флуд-баны на
   аккаунт, требования Telegram API Terms (раскрытие использования API, согласие
   пользователя), хранение сессии — это полный доступ к аккаунту. Это **не**
   «сбор чужих сессий», но формально пересекается с запретом из раздела 6 ТЗ,
   поэтому без вашего явного решения не реализую.
3. Отказ от просмотров в MVP.

**Решение (ADR-013): в MVP — вариант 1, ручной ввод.**

Важно: для ОРД рекламораспространитель ежемесячно передаёт **показы** креатива.
Без варианта 2 показы придётся вносить вручную.

## 5. План аналитики (этап 5)

1. Сбор: снимки подписчиков (по умолчанию каждые 30 мин), события реакций,
   `chat_member`, клики. Каждая запись: `measuredAt`, `source`
   (`telegram_api` / `system` / `manual` / `mtproto`), `methodVersion`.
2. Отображение: четыре визуальных класса — факт Telegram, измерение системы,
   расчётная оценка (с формулой и окном), недоступно. Отсутствие данных — пустая
   ячейка «нет данных», никогда не 0.
3. Рекламная эффективность: Δ подписчиков в окне [T−24ч; T+24ч/72ч/7д] с
   базовой линией (средний дневной прирост за 7 дней до размещения) —
   «наблюдаемое изменение», не «привлечено». Цена подписчика = цена / Δ, только при
   Δ > 0 и с явной пометкой «оценка».
4. Лучшее время: группировка по дню/часу, минимальный порог выборки (например,
   ≥ 5 постов в ячейке), иначе «недостаточно данных».
